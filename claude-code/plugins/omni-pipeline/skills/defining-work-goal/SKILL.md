## 이 지침이 하는 일

- 일을 시작할 때 목표·시작·종료를 정하고, 끝날 때까지 그 정의를 나침반으로 쓴다.
- 길을 잃지 않게 한다 — 단계가 바뀌거나 문맥이 줄어도 정의로 돌아와 지금 하는 일이 목표 안인지 본다.
- 완성도를 지킨다 — 요구 하나하나가 「됨·미룸·못함」 중 하나로 끝나고, 빠진 것 없이 보고된다.
- 플랜·비판 검토·구현·리뷰 순서는 `running-dev-pipeline` 이 정본이다. 여기 다시 적지 않는다.

## 1. 처음 정의할 때

### 정의 전에 확인할 것(읽기만, 파일을 바꾸지 않는다)

1. 작업 자리
   - `git branch --show-current`, `git log --oneline origin/main..HEAD` — 어느 브랜치이고 앞선 커밋이 있는지.
   - `docs/superpowers/plans`·`specs`·`tasks/issues` 에서 티켓 번호·기능 이름으로 기존 기록을 찾는다. 없으면 「기록 없음·새 작업」이라고 적는다.
2. 지금 코드
   - 화면 파일, 그 화면이 여는 컴포넌트, `lib/api/web/<영역>/` 호출부, 백엔드 서비스를 직접 연다.
   - DB 표는 정의 파일보다 실제 DB(`\d 스키마.표`)를 먼저 본다. 칸 이름만 보고 뜻을 짐작하지 않고 참조 표까지 본다.
   - 시안·요청과 지금 코드를 열·칸·단추·문구·상태 값 단위로 대조한다.
3. 영향 범위
   - 바꿀 화면의 데이터를 다른 화면이 같이 쓰는지 찾는다(공용 훅·공용 계산 함수의 호출처).
4. 앞서 한 말 점검
   - 확인 중 앞 답변이 틀린 것을 찾으면 정의 맨 위에 「정정」으로 먼저 밝힌다.

### 정의 형식

1. **목표** — 무엇을 어느 화면·경로에 만드는지 한두 줄. **범위 밖**(뒤로 미룬 일)도 적는다.
2. **요구 목록** — 근거(시안·요청 문장·이슈)에서 뽑은 요구를 한 줄씩. 시안이면 문구·열·칸·단추·배지·상태마다 한 줄. 이 목록이 완성도의 기준이다.
3. **시작** — 첫 단계, 플랜이 다룰 단위, 따를 기존 코드 방식(파일 경로).
4. **종료** — 명령이나 화면 확인으로 판정할 수 있는 조건 목록.
   - 요구 목록의 모든 줄이 「됨·미룸·못함(이유)」 중 하나로 표시된다.
   - 시험은 관련 묶음만. 전체 pytest·vitest·build 는 넣지 않는다. tsc 는 「허락 시」로 적는다.
   - 리뷰 Blocker·High 0건, 플랜 status·체크박스·ledger 갱신.
   - 커밋·푸시는 「지시가 있을 때만」.
5. **정할 것** — 결과를 크게 바꾸는 결정만, 맨 아래 표(질문 | 선택지 | 권장). 권장 근거가 없으면 「근거 없음」.

- 사용자 확인 전에는 착수하지 않는다.
- 확인을 받으면 정의(목표·범위 밖·요구 목록·종료·정해진 결정)를 플랜 문서 맨 앞 「목표·시작·종료」 절에 그대로 옮긴다. 대화가 줄어도 이 절이 남아 있어야 다시 길을 찾는다.

## 2. 진행 중 다시 볼 때

아래 때마다 플랜의 「목표·시작·종료」 절을 다시 읽는다 — 기억으로 대신하지 않는다.

| 때 | 확인할 것 |
|---|---|
| 단계가 바뀔 때(플랜 → 구현 → 리뷰 → 화면 확인) | 다음 단계에 넘기는 지시가 요구 목록·범위 밖과 맞는가 |
| 문맥이 압축된 뒤 | 지금 단계, 끝난 요구, 남은 요구, 정해진 결정 |
| 작업 중 새 요청이 올 때 | 목표 안인가. 밖이면 범위 밖에 적고, 넣을지는 사용자에게 묻는다 |
| 리뷰·비판 지적이 올 때 | 고치는 것이 목표 안의 결함인가, 범위를 넓히는 개선인가 |
| 플랜과 다르게 해야 할 때 | 왜 다른지와 영향을 플랜에 적고 보고한다 |
| 결정이 새로 정해질 때 | 「정할 것」에서 「정해진 결정」으로 옮겨 적는다 |

- 목표 밖 개선을 끼워 넣지 않는다. 진행 중인 목표에 필요한 일은 미루지 않는다.
- 목표 자체가 바뀌면 정의를 고치고 사용자 확인을 다시 받는다.

## 3. 끝낼 때

- 종료 조건을 하나씩 실제 명령·화면으로 확인하고, 그 결과로 보고한다.
- 요구 목록을 표로 보고한다 — 됨 / 미룸(무엇 때문에, 언제) / 못함(이유). 「거의 됨」은 쓰지 않는다.
- 플랜과 다르게 한 점, 범위 밖으로 남긴 일을 함께 적는다.
- 종료 조건 하나라도 확인하지 못했으면 「끝」이라고 하지 않고, 빠진 증거를 적는다.

## 백엔드를 나중에 붙이는 화면 작업일 때

- 서버에 아직 없는 값도 호출 함수까지 만든다. 함수 이름·요청 모양·응답 타입을 두고, 경로는 주석에 「예정」으로 표시한다.
- 종료 조건에 「예정 경로 목록이 명령 하나로 나온다」(예: `rg -n "예정" <호출부 파일>`)를 넣는다 — API 작업 때 필요한 엔드포인트 목록이 된다.
- 「정할 것」에 서버가 없는 동안 화면을 어떻게 채울지(견본 값 / 「준비 중」으로 비움)와, 지금 실제 데이터로 도는 기능이 끊기는지를 넣는다.

## 흔한 실수

- 코드를 열기 전에 시안·기억만으로 목표를 쓴다.
- 요구 목록 없이 「시안대로」라고만 적어, 끝날 때 무엇이 빠졌는지 셀 수 없다.
- 정의를 대화에만 두고 플랜에 옮기지 않아, 압축 뒤 목표를 잃는다.
- 단계가 바뀔 때 정의를 다시 읽지 않고 기억으로 다음 지시를 쓴다.
- 리뷰 지적이나 새 아이디어를 목표 확인 없이 범위에 넣는다.
- 공용 데이터를 쓰는 다른 화면을 빼먹는다.
- 「끝났다」를 명령으로 판정할 수 없는 말로 쓴다.
