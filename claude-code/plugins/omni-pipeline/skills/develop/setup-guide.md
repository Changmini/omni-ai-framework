# 구성 판단 안내

변경마다 구성(혼자 / 리뷰 포함 / 분업)을 정하는 기준이다. 판단은 **router 에이전트**가 하고, 팀장은 입력을 넘기고 결과를 따른다. 질문을 보고 어느 길로 보낼지 먼저 정하는 RAG 의 분기처럼, 이 판단을 대화와 떨어진 곳에서 매번 같은 기준으로 하기 위해서다.

router 는 대화를 모른다. 팀장이 넘긴 입력과 저장소만 보고 정한다. 그래서 팀장의 기대나 대화 분위기에 끌려 가벼운 구성을 고르지 않는다.

## 1. 언제 부르나

| 시점 | 팀장이 넘기는 것 | router 가 정하는 것 |
|---|---|---|
| 1차: 요청을 받은 직후 | 요청 정리문(2절) | 혼자 / SPEC 필요, 범위 메모 |
| 2차: SPEC 승인 뒤 | SPEC 경로, 세션이 길어졌는지 | 리뷰 포함 / 분업, 작업 묶음 |
| 다시 판정: 보고 직전 | 기준 커밋, 지금 구성, SPEC 경로(있으면) | 그대로 / 리뷰 포함으로 올림 |

- 사용자가 「혼자 해」, 「리뷰 받아」, 「분업해」처럼 구성을 직접 정했으면 1차·2차는 부르지 않는다. 다시 판정은 언제나 부른다.
- 구현 중에 범위가 크게 바뀌면(바꿀 곳 밖의 모듈을 건드려야 함) 그때 다시 판정을 한 번 더 부를 수 있다.

## 2. 요청 정리문 (1차 입력)

router 는 대화를 모르므로, 팀장이 판단에 필요한 것을 정리해 넘긴다. 사용자의 말을 그대로 붙이지 않고 동작 문장으로 쓴다.

```
요청 정리문
- 요청: 열린 주문에서 상품 일부 수량만 취소한다. 이유: 상품 하나를 잘못 담은 주문이 가장 흔한 취소 사유.
- 사용자가 밝힌 조건: 결제된 주문은 이번에 다루지 않는다.
- 사용자가 정한 것: 없음
- 관련 이름: 주문 취소, OrderService
- 대화에서만 나온 위험: 쿠폰을 쓴 주문에서 문제가 자주 난다고 함
```

- 「대화에서만 나온 위험」은 코드만 봐서는 알 수 없는 것이다. 빠뜨리면 router 가 위험을 놓친다.
- router 결과에 팀장이 아는 사실이 빠졌으면, 결과를 고치지 말고 그 사실을 정리문에 더해 다시 부른다.

## 3. 범위 조사 (router)

### 3-1. 읽을 것

1. 프로젝트 설정(규칙 파일의 「Agent pipeline」 절): 구성 기준, 위험한 곳(추가), 범위 밖. 없으면 아래 기본값.
2. 요청에 나온 이름을 검색해 정의를 연다.
3. 한 단계 더 따라간다: 그 코드를 부르는 곳, 같은 데이터(표·파일·상태)를 쓰는 곳, 관련 시험.
4. 범위 밖으로 적힌 곳을 건드려야 하면 그 자체를 「모르는 것」으로 적는다.

### 3-2. 세는 법

- **소스 파일**: 바뀔 것으로 보이는 코드 파일. 시험, 문서, 생성되는 파일(빌드 결과·잠금 파일)은 세지 않는다. 새로 만들 파일은 센다. 이름만 바뀌는 import 수정도 한 파일로 센다.
- **모듈**: 프로젝트 설정에 정의가 있으면 그것. 없으면 코드의 최상위 묶음 하나(예: Python 패키지, Java 도메인 패키지, `src/` 바로 아래 폴더). 같은 모듈 안의 파일 여럿은 모듈 하나다.
- 추정이 범위로 나오면(2~4개) 큰 쪽으로 판단한다.

### 3-3. 위험한 곳 찾기

아래 단서로 찾고, **바뀔 줄이 실제로 그 계산·검사·형식에 닿는지** 열어서 확인한다. 이름에 단어가 들어 있다고 위험한 것은 아니다.

| 위험한 곳 | 찾을 단서 | 위험인 경우 / 아닌 경우 |
|---|---|---|
| 금액·결제·정산 | price, amount, total, fee, discount, tax, refund, 금액, 결제, 정산 | 금액 계산식·반올림·통화가 바뀜 / 금액을 화면에 보여 주기만 함 |
| 데이터 삭제·형식·이전 | delete, drop, truncate, migration, schema, ALTER, 직렬화 | 저장된 값이나 그 형식이 바뀌거나 지워짐 / 읽기 조건만 바뀜 |
| 인증·권한·비밀 | auth, login, token, session, permission, role, secret, password | 누가 무엇을 할 수 있는지가 바뀜 / 로그 문구만 바뀜 |
| 다른 코드가 쓰는 인터페이스 | 공개 API 경로, 다른 모듈이 부르는 함수, 파일·메시지 형식 | 인자·반환·형식이 바뀜 / 안쪽 구현만 바뀜 |
| 동시성·트랜잭션·재시도 | lock, transaction, retry, async, queue, job, cron | 순서·잠금·재시도 동작이 바뀜 / 그 안의 계산 한 줄만 바뀜 |

프로젝트 설정의 「위험한 곳(추가)」도 같은 방법으로 본다. 정리문의 「대화에서만 나온 위험」은 확인 없이 위험한 곳으로 센다.

### 3-4. 모르는 것

요청과 코드 어디에도 답이 없고, 고르는 답에 따라 결과가 달라지는 선택이다.

- 모르는 것이다: 「같은 상품이 두 줄이면 어느 줄을 줄이나」(코드가 정하지 않음).
- 모르는 것이 아니다: 「취소 뒤 재고를 푸는가」(기존 `release` 가 있고 전체 취소가 이미 그렇게 함). 코드가 답하면 근거를 적고 넘어간다.

## 4. 1차 판단 규칙

위에서부터 처음 맞는 것을 고른다.

| 번호 | 조건 | 구성 |
|---|---|---|
| 1-1 | 사용자가 구성을 정함 | 그대로 (router 를 부르지 않음) |
| 1-2 | 소스 파일이 혼자 기준(기본 1~2개) 안이고, 모르는 것 0개, 위험한 곳 0개 | 혼자 |
| 1-3 | 그 밖 모두 | SPEC 필요 |

- 문서·주석·시험만 바뀌는 변경은 소스 파일 0개로 보고 1-2 를 적용한다.
- 위험한 곳이 하나라도 있으면 파일이 하나여도 SPEC 필요다. 금액 반올림 한 줄도 마찬가지.
- 확신이 낮으면(5절) SPEC 필요로 정한다. 혼자로 잘못 골라 다시 하는 비용이 SPEC 을 쓰는 비용보다 크다.

## 5. 2차 판단 규칙

승인된 SPEC 의 「바꿀 곳」을 기준으로 다시 센다(3-2). 위에서부터 처음 맞는 것을 고른다.

| 번호 | 조건 | 구성 |
|---|---|---|
| 2-1 | 사용자가 구성을 정함 | 그대로 |
| 2-2 | 소스 파일이 분업 기준(기본 6개) 이상이거나, 모듈이 분업 기준(기본 3개) 이상 | 분업 |
| 2-3 | 서로 독립인 작업 묶음이 둘 이상 | 분업 |
| 2-4 | 팀장이 「세션이 길어 새로 시작하는 편이 낫다」고 넘김 | 분업 |
| 2-5 | 그 밖 모두 | 리뷰 포함 |

**독립인 묶음**: 두 묶음이 같은 파일을 바꾸지 않고, 한쪽이 새로 만드는 함수·자료·형식을 다른 쪽이 쓰지 않는다. 한쪽 결과를 기다려야 하면 독립이 아니다. 분업이면 묶음마다 요구 번호(R1–R3 등)를 적어 돌려준다.

요구가 모호했다는 것은 분업 이유가 아니다. 모호함은 SPEC 이 이미 풀었다.

## 6. 다시 판정 규칙

`git diff --stat <기준 커밋>` 과 커밋 안 된 변경으로 실제 바뀐 소스 파일을 세고, 3-3 으로 위험한 곳을 다시 본다.

| 번호 | 지금 구성 | 실제 변경 | 결과 |
|---|---|---|---|
| 3-1 | 혼자 | 혼자 기준을 넘었거나 위험한 곳을 건드림 | 리뷰 포함으로 올림 |
| 3-2 | 리뷰 포함·분업 | SPEC 「바꿀 곳」 밖 파일을 바꿈 | 그대로, 그 파일 목록을 돌려줌 |
| 3-3 | 어느 구성이든 | 기준 안 | 그대로 |

가벼운 구성으로 내리는 결과는 내지 않는다.

## 7. 확신

- **높음**: 바뀔 곳을 열어 확인했고, 규칙이 하나로 정해진다.
- **낮음**: 검색으로 다 찾았는지 자신이 없거나(동적 호출, 문자열로 부르는 코드), 기준값 바로 위아래거나, 위험한 곳 판단이 애매하다.

낮으면 더 무거운 구성으로 정하고, 무엇 때문에 낮은지 한 줄로 적는다. 사용자만 답할 수 있는 것이면 「팀장에게」에 질문으로 적는다.

## 8. 돌려주는 형식

```
판단: 1차 | 2차 | 다시 판정
구성: 혼자 | SPEC 필요 | 리뷰 포함 | 분업 | 그대로 | 리뷰 포함으로 올림
맞은 규칙: <번호> — <조건>
범위 메모 (1차만):
- 바뀔 곳(추정): <파일 — 무엇을> … (소스 파일 n개, 모듈 m개)
- 위험한 곳: <종류 — 파일:줄, 없으면 "없음">
- 모르는 것: <선택지가 갈리는 것, 없으면 "없음">
작업 묶음 (2차 분업만): 묶음 A (R1–R3): <파일> / 묶음 B (R4–R5): <파일>
바꿀 곳 밖 파일 (다시 판정만): <목록, 없으면 "없음">
근거: <파일:줄> …
확신: 높음 | 낮음 — <이유>
팀장에게: <사용자에게 물을 것, 없으면 "없음">
```

## 9. 팀장이 결과를 받으면

1. 근거 몇 개를 열어 사실인지 본다. 틀린 근거가 있으면 그 점을 정리문에 적어 다시 부른다.
2. 한 줄로 알린다: `구성(1차): SPEC 필요 — 1-3, 금액(쿠폰 재계산), 모르는 것 2개`.
3. 결과를 직접 뒤집지 않는다. 더 가볍게 하려면 사용자에게 묻고, 사용자가 정한 것을 따른다(1-1, 2-1).
4. 「팀장에게」의 질문은 인터뷰(3-2) 첫 질문으로 쓴다.

## 10. 예시

| 요청 | 결과 | 맞은 규칙 |
|---|---|---|
| README 제목의 오타 수정 | 혼자 | 1-2 (소스 0개) |
| 이름이 공백이면 사용자 생성을 거절 | 혼자 | 1-2 (users 1개, 모르는 것·위험 없음) |
| 환불 금액을 줄마다 내림하도록 변경, 함수 하나 | SPEC 필요 | 1-3 (금액) |
| 데이터 내보내기, 어떤 형식인지 정해지지 않음 | SPEC 필요 | 1-3 (모르는 것: 형식, 포함할 열) |
| SPEC 의 바꿀 곳 2개 파일, 모듈 2개 | 리뷰 포함 | 2-5 |
| SPEC 의 바꿀 곳 8개 파일, 결제·알림 묶음이 파일을 나누지 않음 | 분업 | 2-2, 묶음 A·B |
| 혼자로 시작했는데 날짜 표시 수정이 결제·청구 모듈까지 4개 파일로 번짐 | 리뷰 포함으로 올림 | 3-1 |
