# SPEC 쓰는 법

구현자와 리뷰어는 대화를 듣지 못하고 이 파일만 읽는다. 기준은 하나다: **대화를 모르는 사람이 이 파일만으로 구현하고 판정할 수 있는가.** 대화에서 나온 것은 줄이지 않는다.

## 1. 따를 규칙과 위치

작업 중인 프로젝트의 규칙이 먼저다. 아래 순서로 찾고, 처음 찾은 것을 따른다. 저장소 전체를 뒤지지 않고 여기 적은 곳만 본다.

1. **프로젝트 설정**: 규칙 파일의 「Agent pipeline」 절. SPEC 위치·파일 이름·양식이 있으면 그대로 쓴다.
2. **규칙 파일과 그것이 가리키는 문서**: SPEC·설계 문서나 문서 작성(위치, 이름, 양식, 문체, 언어)을 직접 말하는 규칙. 프로젝트가 쓰는 에이전트와 도구마다 파일 이름이 다르다. 예:
   - 여러 에이전트 공용: `AGENTS.md`, `AGENTS.override.md`, 하위 폴더의 `AGENTS.md`
   - 도구별: `CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`, `.github/instructions/*.instructions.md`, `.cursor/rules/`, `.cursorrules`, `.windsurfrules`, `.clinerules`, `CONVENTIONS.md`
   - 사람용: `CONTRIBUTING.md`(루트, `docs/`, `.github/`), `docs/README.md`, `docs/STYLE.md`, `STYLEGUIDE.md`, `docs/CONVENTIONS.md`

   이름은 예시다. 목록에 없어도 그 프로젝트에서 에이전트나 사람에게 작업 규칙을 알려 주는 파일이면 같은 자리로 보고 읽는다.
3. **이미 있는 문서**: SPEC·설계 문서가 모인 폴더가 있으면 그 파일 이름 규칙과 절 구성을 따른다. 흔한 자리:
   - `docs/specs/`, `docs/spec/`, `specs/`, `spec/`
   - `docs/design/`, `docs/designs/`, `design/`, `docs/architecture/`
   - `docs/rfcs/`, `rfcs/`, `docs/proposals/`
   - `docs/adr/`, `docs/decisions/`: 결정 기록이다. SPEC 양식으로 쓰지 않고, 「결정과 이유」를 쓰는 방식만 참고한다.
   - 양식 파일: `TEMPLATE.md`, `_template.md`, `0000-template.md`, `docs/templates/`

   폴더의 문서끼리 양식이 다르면 가장 최근 것을 따른다. 그래도 애매하면 사용자에게 묻는다.
4. **없으면** `docs/specs/<이름>.md` 에 아래 「2. 절 구성」으로 쓴다. `<이름>` 은 짧은 kebab-case(예: `partial-cancel`). 이미 다른 작업의 파일이면 다른 이름.

**따르는 것과 지키는 것**

- 프로젝트 것을 따른다: 위치, 파일 이름, 절 순서와 제목, 문체, 언어.
- 어느 양식이든 지킨다: 요청과 확인 내용, 요구, 시나리오, 제약, 범위 밖, 바꿀 곳, 완료 기준, 결정과 이유. 프로젝트 양식에 자리가 없으면 끝에 덧붙인다.
- 프로젝트 설정의 「SPEC 추가 절」(예: 화면 상태 표, API 요청·응답 예)은 「제약」 앞에 넣는다.
- 2·3에서 찾은 규칙은 10단계 「설정 제안」으로 「Agent pipeline」 절에 적자고 제안한다. 다음부터는 1에서 바로 읽는다.

## 2. 절 구성

```markdown
# <기능> — SPEC
상태: 초안 | 승인 · 날짜: <YYYY-MM-DD> · 구성: <리뷰 포함 | 분업>

## 배경과 목표
## 요청과 확인 내용
## 요구
## 시나리오
## 제약
## 범위 밖
## 바꿀 곳
## 완료 기준
## 결정과 이유
## 열린 질문
```

## 3. 절마다 쓰는 법

**머리**: 상태는 승인 전까지 `초안`. 구성은 2차 판단 뒤에 적는다.

**배경과 목표**: 한 문단. 지금 무엇이 문제이고, 끝나면 무엇이 되는지. 구현 방법은 쓰지 않는다.

**요청과 확인 내용**: 구현자와 리뷰어가 대화 대신 읽는 절. 대화를 옮기지 않고 **SPEC 문장으로 정리하되, 개발에 필요한 내용은 줄이지 않는다.**

- 사용자의 말은 무엇이, 언제, 어떻게 되는지의 동작 문장으로 바꾼다. 예: 「확인을 누르면 알아서 모달창이 닫혀야지」 → 확인 또는 취소 후 선택 창이 닫힘.
- 남길 것: 조건, 숫자, 예로 든 상황, 이유, 고른 것과 버린 것.
- 뺄 것: 욕설, 감정 표현, 말투, 잡담, 개발과 무관한 말, 개인 정보.
- 문구를 그대로 옮기는 것은 그 문구가 결과물일 때만: 화면 문구, 오류 메시지, 사용자가 준 예시 데이터.

묶음:

- 요청: 무엇을, 왜.
- 확인한 것 (Q1, Q2, …): 물은 것, 정한 것(동작 문장), 이유, 버린 안, 간 곳(R·S·D 번호). 바뀌면 지우지 않고 「(바뀜 → Q7)」.
- 추가 요구: 묻지 않았는데 나온 요구·선호를 동작 문장과 이유로, 간 곳(또는 「반영 안 함: 이유」).
- 용어: 사용자의 말과 코드 이름이 다르면 짝.
- 조사에서 찾은 사실: 결정에 쓰인 코드 사실, `파일:줄`.

**요구 (R1, R2, …)**: 요구 하나에 관찰할 수 있는 동작 하나. 입력, 결과, 오류를 밖에서 보이는 이름(함수·명령·화면)으로 적는다. 시안·화면이 근거면 문구·열·칸·단추·상태마다 한 줄. 번호는 지우지 않고, 뺀 요구는 「(삭제: 이유)」로 남긴다.

**시나리오 (S1, S2, …)**: `상태 → 동작 → 결과`. 요구마다 하나 이상, 그리고 정상(가장 흔한 사용), 경계(0, 비어 있음, 최대, 중복, 같은 시각, 정확히 기준값), 오류(잘못된 입력, 없는 대상, 허용되지 않는 상태)를 모두. 오류면 **아무것도 바뀌지 않는지**도 적는다. 끝에 요구 번호를 단다.

**제약**: 바꾸면 안 되는 공개 인터페이스, 이 변경에 해당하는 프로젝트 규칙(**그대로 옮겨 적는다**), 성능·보안·호환 한계.

**범위 밖**: 일부러 하지 않는 것. 리뷰어가 「빠졌다」고 잘못 보고하지 않게.

**바꿀 곳**: 파일마다 `<경로> — <무엇을>`, 시험 파일은 `(시험)`. 마지막 줄에 `소스 파일 n개, 모듈 m개`(2차 판단에 씀). 분업으로 나눌 수 있으면 `묶음 A (R1–R3): …` 처럼 묶고, 묶음끼리 같은 파일을 건드리지 않는다.

**완료 기준 (C1, C2, …)**: 한 줄에 판정 하나, 명령이나 관찰로 참·거짓이 갈리게. 요구·시나리오 번호를 달고, 모든 요구와 시나리오가 어딘가에 걸려야 한다. 마지막은 프로젝트의 전체 시험·린트 명령.

**결정과 이유 (D1, D2, …)**: 정한 것, 이유, 버린 안과 그 이유. 근거가 된 질문 번호를 단다.

**열린 질문**: 승인 전에 0개. 남아 있으면 인터뷰로 돌아간다.

## 4. 좋은 문장과 나쁜 문장

| 나쁨 | 왜 | 좋음 |
|---|---|---|
| 부분 취소를 지원한다 | 무엇이 어떻게 되는지 없음 | R1: `cancel_items(order_id, sku, qty)` 는 그 줄의 수량을 qty 만큼 줄이고 예약 재고를 qty 만큼 푼다 |
| 오류를 적절히 처리한다 | 판정할 수 없음 | R4: qty 가 0 이하이거나 줄 수량보다 크면 입력 오류, 주문·재고는 그대로 |
| 사용자는 확인 창을 원하지 않는다 | 뭉뚱그려 이유·조건이 빠짐 | 추가 요구: 취소는 확인 창 없이 바로 반영된다. 이유: 한 번 더 묻는 창이 손님에게 불편하다 |
| 「확인을 누르면 알아서 모달창이 닫혀야지」 | 말을 그대로 옮김 | 확인 또는 취소 후 선택 창이 닫힘 |
| 잘 동작한다 | 완료 기준이 될 수 없음 | C3: `<시험 명령> <주문 시험>` 통과 |

## 5. 점검 목록

- [ ] 대화를 모르는 사람이 이 파일만으로 구현할 수 있다.
- [ ] 요청 이후 개발에 관한 말마다 SPEC 에 자리가 있고, 조건·이유·예가 빠지지 않았다.
- [ ] 사용자 말을 그대로 옮긴 곳이 없다(화면 문구·오류 메시지·예시 데이터 제외). 욕설·잡담·개인 정보가 없다.
- [ ] 요구마다 시나리오가 있고 정상·경계·오류가 모두 있으며, 오류마다 「바뀌지 않음」 여부가 있다.
- [ ] 프로젝트의 문서 규칙(위치, 이름, 양식, 문체, 언어)을 따랐고, 필수 절은 빠지지 않았다.
- [ ] 관련 프로젝트 규칙이 제약에, 프로젝트 설정의 「SPEC 추가 절」이 SPEC 에 있다.
- [ ] 바꿀 곳에 파일·모듈 합계가 있다.
- [ ] 모든 요구·시나리오가 완료 기준에 걸려 있고, 완료 기준은 모두 명령·관찰로 판정된다.
- [ ] 구현 방법을 요구로 강제하지 않았다. 필요하면 결정과 이유에 적었다.
- [ ] 열린 질문이 0개다.

## 6. 전체 예시

한 예시 프로젝트의 SPEC 이다. 파일 이름과 `<시험 명령>`은 그 프로젝트의 것으로 바꿔 읽는다.

```markdown
# 주문 부분 취소 — SPEC
상태: 승인 · 날짜: 2026-11-26 · 구성: 리뷰 포함

## 배경과 목표
지금은 주문 전체만 취소할 수 있어, 상품 하나만 빼려면 주문을 취소하고 다시 만들어야 한다.
이 변경으로 열린 주문에서 상품 줄의 일부 수량만 취소할 수 있다.

## 요청과 확인 내용
### 요청
- 열린 주문에서 상품 일부 수량만 취소한다. 이유: 상품 하나를 잘못 담은 주문이 가장 흔한 취소 사유다.

### 확인한 것
- Q1 같은 상품 줄이 둘일 때 줄일 줄 → 첫 줄부터 줄어든다. 이유: 그런 주문이 드물다. 버린 안: 비율로, 오류 → D1
- Q2 마지막 줄까지 뺀 주문 → 주문이 취소된다. 이유: 빈 열린 주문을 남기지 않는다. 버린 안: 오류, 빈 주문으로 둠 → R3, D2
- Q3 결제된 주문 → 부분 취소 대상이 아니다. 부분 환불은 다음 변경 → R4, 범위 밖

### 추가 요구
- 취소는 확인 창 없이 바로 반영된다. 이유: 한 번 더 묻는 창이 손님에게 불편하다 → 범위 밖(이 변경에는 화면이 없음)
- 쿠폰을 쓴 주문의 금액이 맞아야 한다. 이유: 문제가 가장 자주 나는 곳 → S2, 제약(금액 규칙)

### 용어
- 「상품 몇 개만 빼기」 → `OrderService.cancel_items`

### 조사에서 찾은 사실
- 주문 만들기는 같은 상품을 한 줄로 합치지 않는다 (orders.py:28)
- 재고 해제 `inventory.release(sku, qty)` 가 이미 있다 (inventory.py:41)

## 요구
- R1: `OrderService.cancel_items(order_id, sku, qty)` 는 그 상품 줄의 수량을 qty 만큼 줄이고, 예약한 재고를 qty 만큼 푼다.
- R2: 소계·할인·합계를 다시 계산한다. 쿠폰 최소 금액 아래로 내려가면 할인은 0이다.
- R3: 줄 수량이 0이 되면 그 줄을 없앤다. 모든 줄이 없어지면 주문 상태는 `cancelled` 가 된다.
- R4: qty 가 0 이하이거나 줄 수량보다 크면, 또는 그 상품 줄이 없으면 입력 오류. 열린 주문이 아니면 주문 오류.
- R5: 바뀐 주문(복사본)을 돌려준다.

## 시나리오
- S1 (정상): A 3개·B 1개 → A 2개 취소 → A 1개·B 1개, A 예약 1, 합계 3,500원 (R1, R2, R5)
- S2 (경계): 쿠폰 TEN(10%, 최소 3,000원), A 2개·B 1개(4,500원) → B 1개 취소 → 합계 2,000원, 할인 0 (R2)
- S3 (경계): A 2개 → A 1개씩 두 번 취소 → 상태 cancelled, 이벤트 order.cancelled 한 번 (R3)
- S4 (오류): A 2개 → A 3개 / 0개 / -1개 / C 1개 취소 → 입력 오류, 주문·재고 그대로 (R4)
- S5 (오류): 결제된 주문 → 취소 → 주문 오류, 그대로 (R4)

## 제약
- create_order, pay, cancel, get_order, list_orders 의 인자와 반환은 바꾸지 않는다.
- 프로젝트 규칙: 주문 상태가 바뀌면 `events.publish("order.<새 상태>", {"order_id": id})` 를 한 번 부른다.
- 프로젝트 규칙: 금액은 원 단위 정수, 할인은 내림.

## 범위 밖
- 결제된 주문의 부분 환불 (Q3)
- 같은 상품 줄 합치기
- 취소 화면과 확인 창

## 바꿀 곳
- orders.py — cancel_items 추가
- test_orders.py — 시험 추가 (시험)
- 합계: 소스 파일 1개, 모듈 1개 (inventory 는 기존 release 호출만)

## 완료 기준
- [ ] C1 S1–S2 시험 통과 — `<시험 명령> <부분 취소 시험>` (R1, R2, R5)
- [ ] C2 S3: order.cancelled 가 정확히 한 번 (R3, 제약)
- [ ] C3 S4–S5: 오류, 주문·재고 그대로 (R4)
- [ ] C4 기존 검사 — `<시험 명령>` 모두 통과

## 결정과 이유
- D1: 같은 상품 줄이 둘이면 첫 줄부터 줄인다(Q1). 지금 그런 주문이 드물고(orders.py:28), 비율로 줄이면 금액 끝수가 생겨 버렸다.
- D2: 마지막 줄을 빼면 오류 대신 주문을 취소한다(Q2). 빈 열린 주문이 생기지 않게.

## 열린 질문
- 없음
```
