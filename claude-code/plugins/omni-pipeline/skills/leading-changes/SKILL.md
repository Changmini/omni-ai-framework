# 팀장으로 변경 이끌기

대화는 팀장(이 세션)에서만 한다. 구현자와 리뷰어는 대화를 듣지 못하고, 팀장이 건넨 파일만 본다. 그래서 SPEC 이 모두가 읽는 하나뿐인 기준이다.

구성은 세 가지다. 변경마다 아래 진행 2·4단계에서 고른다.

| 구성 | 누가 구현하나 | SPEC | 독립 리뷰 |
|---|---|---|---|
| **혼자** | 이 세션 | 없음(완료 기준만 답에) | 없음 |
| **리뷰 포함** | 이 세션 | 있음 | 리뷰어 에이전트 |
| **분업** | 구현자 에이전트 | 있음 | 리뷰어 에이전트 |

아래 목록을 답에 옮겨 적고, 진행에 맞춰 고친다. 각 단계의 자세한 방법은 같은 번호의 절에 있다.

예시의 파일 이름은 한 예시 프로젝트의 것이고, `<시험 명령>`은 그 프로젝트의 시험 명령으로 바꿔 읽는다(예: Python `python3 -m unittest`, Java `./gradlew test`, JavaScript `npm test`). 실제 명령은 프로젝트 규칙과 `omni-core:verifying-changes`가 찾은 것을 쓴다.

```
진행:
- [ ] 1. 범위 조사: 바뀔 곳·위험한 곳·모르는 것을 범위 메모로
- [ ] 2. 1차 판단: 혼자인가, SPEC 이 필요한가
- [ ] 3. 완료 기준과 SPEC: 혼자는 완료 기준만, 그 밖은 인터뷰 → SPEC → 승인
- [ ] 4. 2차 판단: SPEC 으로 리뷰 포함인지 분업인지 확정
- [ ] 5. 구현: 혼자·리뷰 포함은 직접, 분업은 구현자에게
- [ ] 6. 검증: 완료 기준을 하나씩 명령으로 확인
- [ ] 7. 리뷰: 리뷰 포함·분업은 리뷰어에게
- [ ] 8. 차이 처리: 차이마다 판단하고 5로 (리뷰 최대 3회)
- [ ] 9. 실제 변경으로 다시 판정: diff 가 고른 구성의 기준을 넘었는지
- [ ] 10. 보고: 완료 기준마다 근거와 함께
```

## 1. 범위 조사

구성을 고르기 전에, 무엇이 바뀔지 짧게 조사한다. SPEC 처럼 시나리오를 다 쓰지는 않으므로 판단은 추정이다. 추정을 덜 틀리게 하는 것이 이 단계의 목적이다.

1. 프로젝트 규칙 파일(`AGENTS.override.md`, `AGENTS.md`, `CLAUDE.md`)을 읽는다. 특히 「Agent pipeline」 절의 SPEC 위치·양식, 시험 명령, 범위 밖 서비스, 구성 기준.
2. 요청에 나온 기능·함수·데이터 이름을 검색한다(Grep). 그 정의와 부르는 곳을 연다.
3. 바뀔 곳이 건드리는 다른 코드를 한 단계 더 따라간다: 부르는 쪽, 같은 데이터를 쓰는 쪽, 관련 시험.
4. 아래 형식으로 **범위 메모**를 답에 적는다.

```
범위 메모
- 요청: <한 줄>
- 바뀔 곳(추정): <파일 — 무엇을>, …  (소스 파일 n개, 모듈 m개)
- 위험한 곳: <아래 목록 중 해당하는 것, 없으면 "없음">
- 모르는 것: <사용자에게 물어야 정해지는 것, 없으면 "없음">
```

**위험한 곳**(이 스킬 전체에서 같은 뜻으로 쓴다):

- 금액·결제·정산 계산
- 데이터 삭제, 저장 형식·스키마 변경, 데이터 이전
- 인증, 권한, 비밀 정보
- 다른 코드나 외부가 쓰는 인터페이스: 공개 API, 다른 모듈이 부르는 함수의 인자·반환, 파일·메시지 형식
- 동시성, 트랜잭션, 재시도처럼 실패가 늦게 드러나는 곳

예:

```
범위 메모
- 요청: 열린 주문에서 일부 수량만 취소
- 바뀔 곳(추정): orders — cancel_items 추가, inventory — release 호출만 (소스 파일 1개, 모듈 2개)
- 위험한 곳: 금액·결제 계산(쿠폰 재계산)
- 모르는 것: 같은 상품 줄이 둘이면 어느 줄을 줄이나, 마지막 줄을 빼면 주문 상태는?
```

## 2. 1차 판단

범위 메모만으로 **혼자**인지, **SPEC 이 필요한지**를 정한다. 리뷰 포함과 분업의 구분은 SPEC 이 범위를 정한 뒤(4단계)에 한다. 파일 수는 SPEC 을 써야 제대로 보이기 때문이다.

위에서부터 처음 맞는 것을 고른다.

1. **사용자가 정했다**: 「혼자 해」, 「리뷰 받아」, 「분업해」처럼 말했으면 그대로 따른다(분업·리뷰 포함이면 3단계로).
2. **혼자**: 다음이 **모두** 맞을 때.
   - 바뀔 소스 파일(시험·문서 제외)이 1~2개로 추정된다.
   - 「모르는 것」이 없다.
   - 「위험한 곳」이 없다.
3. **SPEC 필요**: 그 밖 모두. 애매하면 이쪽을 고른다. 혼자로 잘못 골라 생기는 비용(빠뜨린 조건, 다시 하기)이 SPEC 을 쓰는 비용보다 크다.

고른 뒤 바로 한 줄로 알린다. 형식: `구성(1차): <혼자 | SPEC 필요> — <맞은 조건>`.

- `구성(1차): 혼자 — 소스 파일 1개, 모르는 것·위험한 곳 없음`
- `구성(1차): SPEC 필요 — 쿠폰 재계산(금액), 모르는 것 2개`

숫자 기준(1~2개)은 기본값이다. 프로젝트 규칙의 「Agent pipeline」 절에 다른 기준이 있으면 그것을 따른다.

## 3. 완료 기준과 SPEC

### 3-1. 혼자: 완료 기준만

구현 전에 완료 기준을 답에 2~5줄로 적는다. 각 줄은 명령이나 관찰로 참·거짓을 가릴 수 있어야 한다.

```
완료 기준
- [ ] `<시험 명령> <사용자 시험>` 통과
- [ ] 이름이 공백뿐이면 입력 오류 (새 시험 「이름 공백」)
- [ ] 기존 시험 모두 통과(`<시험 명령>`)
```

그다음 5단계로 간다(4단계 없음).

### 3-2. 인터뷰

범위 메모의 「모르는 것」부터 묻는다. 끝나는 조건은 하나다: **완료 기준을 추측 없이, 판정할 수 있게 쓸 수 있을 때.**

- 질문 도구(AskUserQuestion)로 한 번에 1~4개씩 묻는다. 선택지를 주고, 추천이 있으면 첫 선택지에 「(추천)」을 붙인다.
- 코드가 이미 답하는 것은 묻지 않는다. 코드에서 찾은 사실은 질문에 근거로 적는다.
- 다룰 것: 정상 동작, 경계 조건(0, 비어 있음, 최대, 중복, 같은 시각), 오류일 때 할 일, 바꾸면 안 되는 것, 범위 밖.
- 답마다 그 자리에서 SPEC 초안의 해당 절에 적는다. 대화로만 정하고 SPEC 에 없으면, 구현자·리뷰어에게는 없는 결정이다.

질문 예:

```
질문: 같은 상품 줄이 둘 있는 주문에서 그 상품을 일부 취소하면 어느 줄을 줄일까요?
- 첫 줄부터 줄인다 (추천) — 지금 주문 만들기가 같은 상품을 줄로 합치지 않음(orders 모듈의 create_order)
- 줄마다 비율로 줄인다
- 같은 상품 줄이 둘 이상이면 오류
```

### 3-3. SPEC 쓰기

**[spec-guide.md](spec-guide.md) 를 읽고 그대로 쓴다.** 위치, 파일 이름, 절 구성, 절마다 쓰는 법, 좋은 문장과 나쁜 문장, 전체 예시가 있다.

요점만:

- 프로젝트 규칙에 SPEC 위치·양식이 있으면 그것을 따른다. 없으면 `docs/specs/<이름>.md`.
- 반드시 들어갈 것: 요구, 시나리오(정상·경계·오류), 제약, 범위 밖, **바꿀 곳**, **완료 기준**, 결정과 이유.
- 「바꿀 곳」은 4단계 판단에 쓰이므로 파일·모듈 단위로 빠짐없이 적는다.

### 3-4. 스스로 점검

사용자에게 보이기 전에 spec-guide.md 의 「점검 목록」을 하나씩 확인한다. 하나라도 걸리면 고친 뒤 보인다.

### 3-5. 승인

SPEC 경로와 요약(요구 수, 시나리오 수, 바꿀 곳, 결정이 필요한 질문)을 보여 주고 승인을 받는다. 승인 전에는 구현하지 않는다. 승인 뒤 결정이 바뀌면 그때 바로 SPEC 을 고치고, 고친 줄을 사용자에게 알린다.

## 4. 2차 판단

승인된 SPEC 의 「바꿀 곳」과 「요구」로 **리뷰 포함**과 **분업** 중 하나를 확정한다.

**분업**: 다음 중 하나라도 맞을 때.

- 바꿀 소스 파일이 6개 이상이거나, 서로 다른 모듈 3개 이상에 걸친다.
- 서로 다른 파일을 바꾸고 서로의 결과를 기다리지 않는 작업 묶음이 둘 이상이다(구현자 여럿이 동시에).
- 인터뷰와 조사로 이 세션의 대화가 이미 길어, 깨끗한 컨텍스트에서 SPEC 만 보고 시작하는 편이 낫다.

**리뷰 포함**: 그 밖 모두.

요구가 모호했다는 것은 분업 이유가 아니다. 모호함은 SPEC 이 이미 풀었다. 구현자를 따로 띄우면 새 세션이 맥락을 다시 모으느라 비용과 시간이 더 들므로, 위 조건일 때만 고른다.

한 줄로 알린다. 형식: `구성(확정): <리뷰 포함 | 분업> — <맞은 조건>`.

- `구성(확정): 리뷰 포함 — 바꿀 곳 소스 파일 2개, 모듈 2개`
- `구성(확정): 분업 — 바꿀 곳 7개 파일, 결제·알림 두 묶음은 서로 독립`

숫자 기준(6개, 3개)은 기본값이다. 프로젝트 규칙에 다른 기준이 있으면 그것을 따른다.

## 5. 구현

### 혼자·리뷰 포함: 이 세션에서 직접

1. 시작 전 기준 커밋을 적어 둔다: `git rev-parse HEAD` → 9단계와 7단계에서 쓴다.
2. 완료 기준을 시험으로 먼저 옮길 수 있으면 먼저 쓴다(실패하는 것을 확인).
3. 작은 단계로 구현한다. 「바꿀 곳」 밖을 고쳐야 하면 멈추고, SPEC 을 고칠지(리뷰 포함) 사용자에게 알릴지 정한다.
4. 구현하다 SPEC 이 틀렸거나 빈 곳을 찾으면 코드로 덮지 않는다. 3-2로 돌아가 사용자에게 묻고 SPEC 을 고친다.

### 분업: 구현자에게

`implementing-specs` 스킬을 따른다. 구현자에게는 SPEC 경로(와 수정 차례면 고칠 차이 파일)만 준다. 대화 요약이나 팀장 메모는 주지 않는다. 2차 판단에서 작업 묶음을 나눴으면 묶음마다 구현자 하나, 요구 번호로 나눠 맡긴다.

## 6. 검증

`omni-core:verifying-changes` 로 프로젝트의 시험·검사를 돌리고, 완료 기준을 하나씩 확인해 결과를 표로 남긴다.

```
| 완료 기준 | 확인 | 결과 |
|---|---|---|
| C1 부분 취소 후 재고 해제 | `<시험 명령> <부분 취소 시험>` | 통과 |
| C2 쿠폰 최소 금액 아래면 할인 0 | 같은 시험의 「쿠폰 제외」 | 통과 |
| C3 기존 시험 | `<시험 명령>` | 14개 통과 |
```

- 실패하면 고치고 다시 돌린다. 통과할 때까지 다음 단계로 가지 않는다.
- 같은 실패를 두 번 고쳐도 계속되면, 세 번째 시도 전에 멈추고 원인 가설을 다시 세운다. 그래도 안 되면 사용자에게 상황을 보이고 묻는다.
- 분업이면 구현자 보고의 근거를 그대로 믿지 않고, 같은 명령을 팀장이 다시 돌린다.

## 7. 리뷰

리뷰 포함·분업에서는 `reviewing-changes` 스킬로 리뷰어에게 맡긴다. 혼자는 이 단계가 없다(9단계에서 다시 판정).

- 리뷰어에게 주는 것: SPEC 경로, 변경 diff 파일(리뷰 포함은 `git diff <기준 커밋>` 으로 커밋 안 된 변경까지, 분업은 구현자 브랜치), 범위 「정확성에 영향을 주는 차이만, 스타일은 넘김」.
- 주지 않는 것: 대화, 팀장이나 구현자의 설명. 리뷰어는 구현 과정을 모르는 눈이라서 의미가 있다.
- 건너뛰지 않는다. 팀장이 diff 를 직접 읽은 것으로 대신하지 않는다.
- 사용자가 단계마다 직접 확인하겠다고 한 리뷰 포함 작업이면, 리뷰어 대신 끝에 `/code-review` 한 번으로 한다.

## 8. 차이 처리

리뷰어가 보고한 차이마다, 해당 파일·줄을 직접 열어 근거를 확인한 뒤 판단한다.

| 차이가 말하는 것 | 할 일 |
|---|---|
| 구현이 SPEC 에 못 미침 | 리뷰 포함: 팀장이 고친다. 분업: 고칠 차이만 파일로 적어 SPEC 경로와 함께 구현자에게(5단계). |
| SPEC 이 틀렸거나 비었음 | 사용자에게 묻고(3-2), SPEC 을 고친 뒤 5단계 |
| 지적이 틀림 | 왜 틀렸는지 한 줄로 적고 버린다 |

판단 기록 예:

```
차이 처리 (리뷰 1회차)
1. R3 마지막 줄 취소 시 이벤트 없음 — orders:71 — 맞음 → 고침
2. S4 음수 수량 — 이미 입력 오류를 냄(orders:62) — 틀린 지적 → 버림
3. 같은 상품 줄 둘 — SPEC 에 없음 → 사용자에게 질문
```

- 고친 뒤 6단계(검증)와 7단계(리뷰)를 다시 한다.
- 리뷰를 3번 돌려도 차이가 남으면 멈추고, 남은 차이와 판단을 사용자에게 보여 주고 어떻게 할지 묻는다.
- 넘길 때는 말로 옮기지 않고 파일과 경로를 넘긴다. 옮길 때마다 내용이 빠진다.

## 9. 실제 변경으로 다시 판정

2·4단계는 추정으로 골랐다. 끝내기 전에 실제 변경으로 다시 확인한다.

1. `git diff --stat <기준 커밋>` 으로 바뀐 소스 파일 수를 센다. 바뀐 곳에 「위험한 곳」이 있는지 본다.
2. 결과에 따라:

| 고른 구성 | 실제 변경이 | 할 일 |
|---|---|---|
| 혼자 | 소스 파일 3개 이상이거나 위험한 곳을 건드림 | 지금까지 정한 것으로 짧은 SPEC 을 쓰고(spec-guide.md), 7단계 리뷰를 붙인다. 사용자에게 알린다 |
| 리뷰 포함·분업 | SPEC 「바꿀 곳」 밖의 파일을 바꿈 | 그 파일마다 이유를 적거나 되돌린다. 이유가 SPEC 범위를 바꾸면 SPEC 을 고치고 7단계를 다시 |
| 어느 구성이든 | 기준 안 | 그대로 10단계 |

예: `다시 판정: 혼자로 했으나 4개 파일(가격 계산 포함) 변경 → 리뷰 포함으로 올림, SPEC docs/specs/price-rounding.md 작성 후 리뷰`.

가벼운 구성으로 내리지는 않는다. 사용자가 말한 경우만 예외다.

## 10. 보고

한국어로, 아래 순서대로.

```
구성: 리뷰 포함 — 쿠폰 재계산(금액), 바꿀 곳 2개 파일
결정: 같은 상품 줄은 첫 줄부터 줄임, 마지막 줄 취소 시 주문 취소 (SPEC D1·D2)
한 일: orders 에 cancel_items 추가, 시험 6개
완료 기준:
- [x] C1 … — `<시험 명령> …` → 통과
- [x] C2 … — …
리뷰: 2회, 차이 3개(고침 2, 틀린 지적 1)
남은 일: 없음
```

- 완료 기준이 하나라도 확인되지 않았으면 「끝」이라 하지 않고, 빠진 근거를 적는다.
- 커밋·푸시는 사용자가 요청할 때만.

## 흔한 실수

- 범위 조사 없이 구성을 골라, 혼자로 시작했다가 위험한 곳을 늦게 만난다.
- 구성을 고르지 않고 매번 분업으로 가서, 작은 변경에 비용과 시간을 두세 배 쓴다.
- 고른 구성과 이유를 알리지 않아, 사용자가 왜 리뷰가 돌았는지(또는 안 돌았는지) 모른다.
- 대화로 정한 결정을 SPEC 에 적지 않아, 구현자·리뷰어가 모른다.
- 구현자에게 SPEC 대신 대화 요약을, 리뷰어에게 구현자의 설명을 같이 넘긴다.
- 리뷰를 「diff 를 직접 읽었다」로 건너뛴다.
- 리뷰 차이를 근거 확인 없이 그대로 구현자에게 넘긴다.
- 완료 기준을 명령으로 판정할 수 없는 말(「잘 동작한다」)로 쓴다.
- 9단계를 건너뛰어, 혼자로 시작한 큰 변경이 리뷰 없이 끝난다.
