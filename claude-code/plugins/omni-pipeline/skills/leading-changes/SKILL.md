# 팀장으로 변경 이끌기

대화는 팀장(이 세션)에서만 한다. 구현자와 리뷰어는 대화를 듣지 못하고 팀장이 건넨 파일만 본다. 그래서 SPEC 이 모두가 읽는 하나뿐인 기준이고, 대화에서 개발에 필요한 것은 줄이지 않고 정리해 SPEC 에 옮긴다.

구성은 세 가지다. 변경마다 2·4단계에서 고른다.

| 구성 | 누가 구현하나 | SPEC | 독립 리뷰 |
|---|---|---|---|
| **혼자** | 이 세션 | 없음(완료 기준만 답에) | 없음 |
| **리뷰 포함** | 이 세션 | 있음 | 리뷰어 에이전트 |
| **분업** | 구현자 에이전트 | 있음 | 리뷰어 에이전트 |

이 스킬의 기준값은 기본값이다. 프로젝트마다 다른 값은 그 프로젝트 규칙 파일의 「Agent pipeline」 절(이하 **프로젝트 설정**)이 정한다. 1단계에서 읽고, 10단계에서 새로 알게 된 것을 제안한다.

아래 목록을 답에 옮겨 적고 진행에 맞춰 고친다. 각 단계는 같은 번호의 절에 있다.

```
진행:
- [ ] 1. 범위 조사: 프로젝트 설정을 읽고 범위 메모를 쓴다
- [ ] 2. 1차 판단: 혼자인가, SPEC 이 필요한가
- [ ] 3. 완료 기준과 SPEC: 혼자는 완료 기준만, 그 밖은 인터뷰 → SPEC → 대화 대조 → 승인
- [ ] 4. 2차 판단: SPEC 으로 리뷰 포함인지 분업인지 확정
- [ ] 5. 구현: 혼자·리뷰 포함은 직접, 분업은 구현자에게
- [ ] 6. 검증: 완료 기준을 하나씩 명령으로 확인
- [ ] 7. 리뷰: 리뷰 포함·분업은 리뷰어에게
- [ ] 8. 차이 처리: 차이마다 판단하고 5로 (리뷰 최대 3회)
- [ ] 9. 실제 변경으로 다시 판정: diff 가 고른 구성의 기준을 넘었는지
- [ ] 10. 보고: 완료 기준마다 근거, 프로젝트 설정 제안
```

**다시 읽을 때**: 단계가 바뀔 때, 대화가 압축된 뒤, 작업 중 새 요청이나 리뷰 지적이 올 때는 기억에 기대지 말고 SPEC(혼자면 완료 기준)을 다시 읽는다. 새 요청이 목표 밖이면 범위 밖에 적고, 넣을지는 사용자에게 묻는다.

예시의 파일 이름은 한 예시 프로젝트의 것이고, `<시험 명령>`은 그 프로젝트의 것으로 바꿔 읽는다(예: `python3 -m unittest`, `./gradlew test`, `npm test`).

## 1. 범위 조사

구성을 고르기 전에 무엇이 바뀔지 짧게 조사한다. 판단은 추정이고, 이 단계는 추정을 덜 틀리게 한다.

1. 규칙 파일(`AGENTS.override.md`, `AGENTS.md`, `CLAUDE.md`)의 「Agent pipeline」 절에서 아래 항목을 찾는다. 없는 항목은 기본값.

   | 설정 | 쓰는 단계 | 기본값 |
   |---|---|---|
   | SPEC 위치·양식 | 3 | `docs/specs/<이름>.md`, spec-guide.md 양식 |
   | 구성 기준 | 2, 4, 9 | 혼자 소스 파일 1~2개, 분업 6개 이상 또는 모듈 3개 이상 |
   | 위험한 곳(추가) | 1, 2, 9 | 아래 공통 목록만 |
   | 인터뷰에서 꼭 물을 것 | 3 | 없음 |
   | SPEC 추가 절 | 3 | 없음 |
   | 시험·검사 명령, 실행 확인 | 6 | `omni-core:verifying-changes` 가 찾은 것 |
   | 리뷰 관점(추가) | 7 | 정확성만 |
   | 범위 밖 | 5, 9 | 없음 |

   절이 아예 없으면, 조사에서 찾은 사실(시험 명령, 금액·권한·마이그레이션이 있는 곳, 기존 SPEC 폴더)로 설정 초안을 만들어 범위 메모와 함께 보인다. 승인받아야만 규칙 파일에 적는다. 거절하면 기본값으로 가고 이 세션에서 다시 묻지 않는다.
2. 같은 작업의 기존 SPEC·기록이 있는지 SPEC 위치에서 찾는다.
3. 요청에 나온 기능·함수·데이터 이름을 검색해 정의와 부르는 곳을 연다. 한 단계 더 따라간다: 부르는 쪽, 같은 데이터를 쓰는 쪽, 관련 시험.
4. **범위 메모**를 답에 적는다.

```
범위 메모
- 요청: 열린 주문에서 일부 수량만 취소
- 프로젝트 설정: 있음 — SPEC 위치 docs/specs/, 위험한 곳에 「재고 수량」 추가
- 바뀔 곳(추정): orders — cancel_items 추가, inventory — release 호출만 (소스 파일 1개, 모듈 2개)
- 위험한 곳: 금액(쿠폰 재계산)
- 모르는 것: 같은 상품 줄이 둘이면 어느 줄을 줄이나, 마지막 줄을 빼면 주문 상태는?
```

**위험한 곳**(이 스킬 전체에서 같은 뜻. 프로젝트 설정의 것을 더한다):

- 금액·결제·정산 계산
- 데이터 삭제, 저장 형식·스키마 변경, 데이터 이전
- 인증, 권한, 비밀 정보
- 다른 코드나 외부가 쓰는 인터페이스: 공개 API, 다른 모듈이 부르는 함수의 인자·반환, 파일·메시지 형식
- 동시성, 트랜잭션, 재시도처럼 실패가 늦게 드러나는 곳

## 2. 1차 판단

범위 메모만으로 **혼자**인지 **SPEC 필요**인지 정한다. 리뷰 포함과 분업의 구분은 파일 수가 SPEC 을 써야 보이므로 4단계에서 한다.

위에서부터 처음 맞는 것을 고른다.

1. **사용자가 정했다**: 「혼자 해」, 「리뷰 받아」, 「분업해」처럼 말했으면 따른다.
2. **혼자**: 바뀔 소스 파일(시험·문서 제외)이 구성 기준 안이고, 「모르는 것」과 「위험한 곳」이 모두 없을 때.
3. **SPEC 필요**: 그 밖 모두. 애매하면 이쪽. 혼자로 잘못 골라 다시 하는 비용이 SPEC 을 쓰는 비용보다 크다.

한 줄로 알린다: `구성(1차): SPEC 필요 — 쿠폰 재계산(금액), 모르는 것 2개`.

## 3. 완료 기준과 SPEC

### 3-1. 혼자: 완료 기준만

구현 전에 완료 기준을 답에 2~5줄로 적는다. 각 줄은 명령이나 관찰로 참·거짓이 갈려야 한다. 그다음 5단계로 간다.

```
완료 기준
- [ ] 이름이 공백뿐이면 입력 오류 (새 시험 「이름 공백」)
- [ ] 기존 시험 모두 통과(`<시험 명령>`)
```

### 3-2. 인터뷰

「모르는 것」과 프로젝트 설정의 「꼭 물을 것」 중 해당하는 것을 묻는다. **완료 기준을 추측 없이 쓸 수 있으면** 멈춘다.

- 질문 도구(AskUserQuestion)로 한 번에 1~4개. 선택지를 주고, 추천은 첫 선택지에 「(추천)」.
- 코드가 답하는 것은 묻지 않고, 찾은 사실을 질문의 근거로 적는다.
- 다룰 것: 정상 동작, 경계(0, 비어 있음, 최대, 중복, 같은 시각), 오류일 때, 바꾸면 안 되는 것, 범위 밖.
- 답을 받을 때마다 **그때 바로** SPEC 초안에 정리해 적는다. 「요청과 대화」에는 고른 답과 그 이유·조건·예를 빠짐없이, 해당 절(요구·제약·결정 등)에는 그 결과를 적는다. 묻지 않았는데 사용자가 한 말 중 개발에 필요한 것(선호, 싫은 것, 예로 든 상황)도 적는다. 대화가 길어지면 앞부분이 압축되어 사라진다.
- 정리는 하되 줄이지 않는다. 대화를 그대로 붙이지 않는다: 욕설·감정 표현·잡담·개인 정보는 빼고, 개발에 필요한 내용은 뭉뚱그리지 않는다. 자세한 기준은 spec-guide.md 「요청과 대화」.

```
질문: 같은 상품 줄이 둘 있는 주문에서 일부 취소하면 어느 줄을 줄일까요?
- 첫 줄부터 (추천) — 주문 만들기가 같은 상품을 합치지 않음(orders 의 create_order)
- 줄마다 비율로
- 같은 상품 줄이 둘 이상이면 오류
```

### 3-3. SPEC 쓰기

**[spec-guide.md](spec-guide.md) 를 읽고 그대로 쓴다.** 위치, 절 구성, 절마다 쓰는 법, 예시가 있다. 「바꿀 곳」은 4단계 판단에 쓰이므로 파일·모듈 단위로 빠짐없이 적는다.

### 3-4. 대화 대조와 점검

보이기 전에 확인하고, 걸리면 고친다.

1. **대화 대조**: 요청 이후 사용자 메시지를 처음부터 다시 읽는다. 개발에 관한 말마다 SPEC 에 자리(요구, 시나리오, 제약, 범위 밖, 결정, 또는 「반영 안 함: 이유」)가 있어야 한다. 없으면 정리해 넣고 자리를 정한다. 잡담이나 감정 표현은 넘어간다.
2. spec-guide.md 의 「점검 목록」.

### 3-5. 승인

SPEC 경로와 요약(요구·시나리오 수, 바꿀 곳, `대화 대조: 사용자 메시지 12개 — 모두 자리 있음`)을 보이고 승인을 받는다. 승인 전에는 구현하지 않는다. 뒤에 결정이 바뀌면 바로 SPEC 을 고치고 고친 줄을 알린다.

## 4. 2차 판단

승인된 SPEC 의 「바꿀 곳」으로 확정한다.

**분업**: 다음 중 하나라도 맞을 때.

- 바꿀 소스 파일이나 모듈 수가 구성 기준의 분업 기준 이상이다.
- 서로 다른 파일을 바꾸고 서로의 결과를 기다리지 않는 작업 묶음이 둘 이상이다.
- 인터뷰와 조사로 대화가 이미 길어, 깨끗한 컨텍스트에서 SPEC 만 보고 시작하는 편이 낫다.

**리뷰 포함**: 그 밖 모두. 구현자를 따로 띄우면 맥락을 다시 모으느라 비용이 더 들므로, 위 조건일 때만 분업한다.

한 줄로 알린다: `구성(확정): 리뷰 포함 — 바꿀 곳 소스 파일 2개, 모듈 2개`.

## 5. 구현

### 혼자·리뷰 포함: 이 세션에서 직접

1. 시작 전 기준 커밋을 적어 둔다(`git rev-parse HEAD`). 7·9단계에서 쓴다.
2. 완료 기준을 시험으로 옮길 수 있으면 먼저 쓰고 실패를 확인한다.
3. 「바꿀 곳」 밖을 고쳐야 하면 멈추고 SPEC 을 고칠지 사용자에게 알릴지 정한다.
4. SPEC 이 틀렸거나 빈 곳을 찾으면 코드로 덮지 않는다. 3-2로 돌아가 묻고 SPEC 을 고친다.

### 분업: 구현자에게

`implementing-specs` 스킬을 따른다. 구현자에게는 SPEC 경로(수정 차례면 고칠 차이 파일도)만 준다. 대화는 SPEC 에 정리되어 들어 있으므로 따로 요약이나 메모를 덧붙이지 않는다. 작업 묶음을 나눴으면 묶음마다 구현자 하나, 요구 번호로 맡긴다.

## 6. 검증

`omni-core:verifying-changes` 로 시험·검사를 돌리고, 완료 기준마다 결과를 표로 남긴다.

```
| 완료 기준 | 확인 | 결과 |
|---|---|---|
| C1 부분 취소 후 재고 해제 | `<시험 명령> <부분 취소 시험>` | 통과 |
| C2 기존 시험 | `<시험 명령>` | 14개 통과 |
```

- 통과할 때까지 다음 단계로 가지 않는다. 같은 실패를 두 번 고쳐도 남으면 원인 가설을 다시 세우고, 그래도 안 되면 사용자에게 묻는다.
- 분업이면 구현자 보고를 믿지 않고 같은 명령을 직접 돌린다.

## 7. 리뷰

리뷰 포함·분업은 `reviewing-changes` 스킬로 리뷰어에게 맡긴다.

- 주는 것: SPEC 경로, diff 파일(리뷰 포함은 `git diff <기준 커밋>`, 분업은 구현자 브랜치), 범위 「정확성에 영향을 주는 차이만」과 프로젝트 설정의 「리뷰 관점」.
- 주지 않는 것: 팀장이나 구현자의 설명. 리뷰어는 구현 과정을 모르는 눈이라서 의미가 있다.
- 건너뛰지 않고, 팀장이 diff 를 읽은 것으로 대신하지 않는다. 사용자가 단계마다 직접 확인한 리뷰 포함 작업만 끝에 `/code-review` 한 번으로 대신한다.

## 8. 차이 처리

차이마다 해당 파일·줄을 직접 열어 근거를 확인하고 판단한다.

| 차이가 말하는 것 | 할 일 |
|---|---|
| 구현이 SPEC 에 못 미침 | 리뷰 포함: 직접 고친다. 분업: 고칠 차이를 파일로 적어 구현자에게(5단계) |
| SPEC 이 틀렸거나 비었음 | 사용자에게 묻고(3-2), SPEC 을 고친 뒤 5단계 |
| 지적이 틀림 | 이유를 한 줄로 적고 버린다 |

```
차이 처리 (리뷰 1회차)
1. R3 마지막 줄 취소 시 이벤트 없음 — orders:71 — 맞음 → 고침
2. S4 음수 수량 — 이미 입력 오류(orders:62) — 틀린 지적 → 버림
```

고친 뒤 6·7단계를 다시 한다. 3회 뒤에도 차이가 남으면 멈추고 남은 차이와 판단을 보여 주고 묻는다.

## 9. 실제 변경으로 다시 판정

`git diff --stat <기준 커밋>` 으로 바뀐 소스 파일 수와 위험한 곳을 본다.

| 고른 구성 | 실제 변경이 | 할 일 |
|---|---|---|
| 혼자 | 혼자 기준을 넘었거나 위험한 곳을 건드림 | 정한 것으로 짧은 SPEC 을 쓰고 7단계 리뷰를 붙인다. 알린다 |
| 리뷰 포함·분업 | 「바꿀 곳」 밖 파일을 바꿈 | 파일마다 이유를 적거나 되돌린다. 범위가 바뀌면 SPEC 을 고치고 7단계를 다시 |
| 어느 구성이든 | 기준 안 | 10단계 |

사용자가 말하지 않는 한 가벼운 구성으로 내리지 않는다.

## 10. 보고

```
구성: 리뷰 포함 — 쿠폰 재계산(금액), 바꿀 곳 2개 파일
결정: 같은 상품 줄은 첫 줄부터, 마지막 줄 취소 시 주문 취소 (SPEC D1·D2)
요구: R1–R4 됨, R5 미룸(사용자 결정, 다음 변경)
완료 기준:
- [x] C1 … — `<시험 명령> …` → 통과
리뷰: 2회, 차이 3개(고침 2, 틀린 지적 1)
남은 일: 없음
```

- 요구마다 됨 / 미룸(이유) / 못함(이유) 중 하나. 「거의 됨」은 쓰지 않는다.
- 완료 기준이 하나라도 확인되지 않았으면 「끝」이라 하지 않고 빠진 근거를 적는다.
- 커밋·푸시는 사용자가 요청할 때만.

**설정 제안**: 다음 변경에도 쓸 것이 나왔을 때만, 프로젝트 설정에 넣을 1~2줄을 보고 끝에 제안한다(늦게 발견한 위험한 곳, 다음에도 물을 질문, 새로 찾은 검사 명령, 덧붙인 SPEC 절). 설정이 길어졌으면 합치거나 뺄 줄도 제안한다. 승인받은 줄만 적는다.

```
설정 제안: 위험한 곳에 「재고 수량 계산(inventory)」 추가 — 이번에 9단계에서 늦게 발견
```

---

## 흔한 실수

- 프로젝트 설정과 범위 조사 없이 구성을 골라, 위험한 곳을 늦게 만난다.
- 대화로 정한 것을 SPEC 에 적지 않거나 뭉뚱그려 적어, 구현자·리뷰어가 조건과 이유를 모른다.
- 대화를 그대로 붙여, 욕설·잡담·개인 정보가 SPEC 에 들어간다.
- 대화 대조 없이 승인받아, 지나가며 한 말이 빠진다.
- 매번 분업으로 가서 작은 변경에 비용을 두세 배 쓴다.
- 리뷰 차이를 근거 확인 없이 구현자에게 넘긴다.
- 9단계를 건너뛰어, 혼자로 시작한 큰 변경이 리뷰 없이 끝난다.
