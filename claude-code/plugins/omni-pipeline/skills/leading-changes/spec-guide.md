# SPEC 쓰는 법

구현자와 리뷰어는 대화를 듣지 못하고 이 파일만 읽는다. 그래서 SPEC 은 「대화 없이 이 파일만으로 구현하고 판정할 수 있는가」로 쓴다.

목차

1. 위치와 이름
2. 절 구성
3. 절마다 쓰는 법
4. 좋은 문장과 나쁜 문장
5. 점검 목록
6. 전체 예시

## 1. 위치와 이름

1. **프로젝트 규칙이 먼저다.** 규칙 파일(`AGENTS.override.md`, `AGENTS.md`, `CLAUDE.md`, 특히 「Agent pipeline」 절의 Specs·Spec template 행, 또는 거기서 가리키는 문서)에 SPEC 위치·파일 이름·양식이 있으면 그대로 따른다.
2. **없으면** `docs/specs/<이름>.md`. `<이름>` 은 변경을 가리키는 짧은 kebab-case(예: `partial-cancel`). 그 파일이 이미 다른 작업의 것이면 다른 이름을 고른다.
3. 프로젝트 양식에 아래 필수 절(요구, 시나리오, 제약, 범위 밖, 바꿀 곳, 완료 기준, 결정과 이유)을 넣을 자리가 없으면, 양식 끝에 그 절을 덧붙인다.

## 2. 절 구성

```markdown
# <기능> — SPEC
상태: 초안 | 승인 · 날짜: <YYYY-MM-DD> · 구성: <리뷰 포함 | 분업>

## 배경과 목표
## 요구
## 시나리오
## 제약
## 범위 밖
## 바꿀 곳
## 완료 기준
## 결정과 이유
## 열린 질문
```

## 3. 절마다 쓰는 법

### 머리

- 상태는 사용자가 승인하기 전까지 `초안`, 승인되면 `승인`으로 바꾸고 날짜를 적는다.
- 구성은 2차 판단 뒤에 적는다.

### 배경과 목표

한 문단. 지금 무엇이 문제이고, 이 변경이 끝나면 무엇이 되는지. 구현 방법은 쓰지 않는다.

### 요구 (R1, R2, …)

- 요구 하나에 관찰할 수 있는 동작 하나. 「~한다」로 끝낸다.
- 입력, 결과, 오류를 적는다. 함수·명령·화면처럼 밖에서 보이는 이름을 그대로 쓴다.
- 번호는 지우지 않는다. 요구를 빼면 줄을 지우지 말고 「(삭제: 이유)」로 남긴다. 리뷰어와 구현자가 번호로 가리키기 때문이다.

### 시나리오 (S1, S2, …)

요구를 실제 상황으로 푼 것. 형식은 `상태 → 동작 → 결과`. 요구마다 최소 하나, 그리고 다음 세 종류를 모두 담는다.

- **정상**: 가장 흔한 사용.
- **경계**: 0, 비어 있음, 최댓값, 같은 값 두 번, 같은 시각, 정확히 기준값.
- **오류**: 잘못된 입력, 없는 대상, 허용되지 않는 상태. 오류일 때 **아무것도 바뀌지 않는지**도 적는다.

각 시나리오 끝에 관련 요구 번호를 단다.

### 제약

바꾸면 안 되는 것과 지켜야 하는 규칙.

- 기존 공개 인터페이스(함수 인자·반환, API, 파일·메시지 형식)
- 프로젝트 규칙 중 이 변경에 해당하는 것을 **그대로 옮겨 적는다**(예: 「상태가 바뀌면 이벤트 한 번」, 「금액은 정수」). 구현자가 규칙 파일을 놓쳐도 SPEC 에서 보게 하기 위해서다.
- 성능, 보안, 호환에 관한 한계

### 범위 밖

이번에 하지 않는 것. 리뷰어가 「빠졌다」고 잘못 보고하지 않게, 사용자가 일부러 뺀 것을 적는다.

### 바꿀 곳

- 파일마다 한 줄: `<경로> — <무엇을: 새로 만듦 / 함수 추가 / 수정>`. 시험 파일도 적되 끝에 `(시험)`을 붙인다.
- 마지막 줄에 합계: `소스 파일 n개, 모듈 m개`. 2차 판단(리뷰 포함 / 분업)이 이 줄로 정해진다.
- 분업에서 구현자를 나눌 수 있으면 묶음으로 적는다: `묶음 A (R1–R3): …`, `묶음 B (R4–R5): …`. 묶음끼리는 같은 파일을 건드리지 않는다.

### 완료 기준 (C1, C2, …)

- 체크박스 한 줄에 판정 하나. 명령이나 관찰로 참·거짓이 갈려야 한다.
- 관련 요구·시나리오 번호를 단다. 모든 요구와 시나리오가 어떤 완료 기준에 걸려 있어야 한다.
- 마지막 항목은 기존 검사 전체: 프로젝트의 시험·린트 명령.
- 구현자는 언제 멈출지, 리뷰어는 무엇으로 판정할지 이 절에서 안다.

### 결정과 이유 (D1, D2, …)

인터뷰와 조사로 정한 것과 그 이유. 「다른 안을 왜 버렸는지」도 짧게. 나중에 리뷰어가 「이건 왜 이렇게 했지?」를 묻지 않게 한다.

### 열린 질문

승인 전에 **0개**여야 한다. 남아 있으면 승인을 받지 않고 인터뷰로 돌아간다.

## 4. 좋은 문장과 나쁜 문장

| 나쁨 | 왜 | 좋음 |
|---|---|---|
| 부분 취소를 지원한다 | 무엇이 어떻게 되는지 없음 | R1: `cancel_items(order_id, sku, qty)` 는 그 상품 줄의 수량을 qty 만큼 줄이고, 예약한 재고를 qty 만큼 푼다 |
| 오류를 적절히 처리한다 | 판정할 수 없음 | R4: qty 가 0 이하이거나 줄 수량보다 크면 입력 오류를 내고, 주문·재고는 바뀌지 않는다 |
| 성능이 좋아야 한다 | 기준 없음 | 제약: 주문 1,000개에서 `page_orders` 한 번이 0.1초 안 (시험 test_perf) |
| 잘 동작한다 | 완료 기준이 될 수 없음 | C3: `<시험 명령> <주문 시험>` 통과 |
| 쿠폰도 고려한다 | 어떻게? | S3: 쿠폰 TEN(최소 3,000원) 주문의 합계가 2,000원이 되면 할인 0 → 합계 2,000원 (R2) |

## 5. 점검 목록

사용자에게 보이기 전에 하나씩 확인한다. 하나라도 「아니오」면 고친다.

- [ ] 대화를 모르는 사람이 이 파일만으로 구현할 수 있다.
- [ ] 요구마다 시나리오가 있고, 정상·경계·오류가 모두 있다.
- [ ] 오류 시나리오마다 「아무것도 바뀌지 않음」 여부가 적혀 있다.
- [ ] 관련 프로젝트 규칙이 제약에 옮겨 적혀 있다.
- [ ] 바꿀 곳에 파일·모듈 합계가 있다.
- [ ] 모든 요구·시나리오가 완료 기준에 걸려 있고, 완료 기준은 모두 명령·관찰로 판정된다.
- [ ] 대화로 정한 것이 모두 「결정과 이유」에 있다.
- [ ] 열린 질문이 0개다.
- [ ] 구현 방법(어떤 자료 구조, 어떤 알고리즘)을 요구로 강제하지 않았다. 필요하면 결정과 이유에 적었다.

## 6. 전체 예시

한 예시 프로젝트의 SPEC 이다. 파일 이름과 `<시험 명령>`은 그 프로젝트의 것으로 바꿔 읽는다(예: Python `python3 -m unittest`, Java `./gradlew test`).

```markdown
# 주문 부분 취소 — SPEC
상태: 승인 · 날짜: 2026-11-26 · 구성: 리뷰 포함

## 배경과 목표
지금은 주문 전체만 취소할 수 있어, 상품 하나만 빼려면 주문을 취소하고 다시 만들어야 한다.
이 변경으로 열린 주문에서 상품 줄의 일부 수량만 취소할 수 있다.

## 요구
- R1: `OrderService.cancel_items(order_id, sku, qty)` 는 그 상품 줄의 수량을 qty 만큼 줄이고, 예약한 재고를 qty 만큼 푼다.
- R2: 소계·할인·합계를 다시 계산한다. 쿠폰 최소 금액 아래로 내려가면 할인은 0이다.
- R3: 줄 수량이 0이 되면 그 줄을 없앤다. 모든 줄이 없어지면 주문 상태는 `cancelled` 가 된다.
- R4: qty 가 0 이하이거나 줄 수량보다 크면, 또는 그 상품 줄이 없으면 ValueError. 열린 주문이 아니면 OrderError.
- R5: 바뀐 주문(복사본)을 돌려준다.

## 시나리오
- S1 (정상): A 3개·B 1개 주문 → A 2개 취소 → A 1개·B 1개, A 재고 예약 1, 합계 3,500원 (R1, R2, R5)
- S2 (경계): 쿠폰 TEN(10%, 최소 3,000원)으로 A 2개·B 1개(4,500원) → B 1개 취소 → 합계 2,000원, 할인 0 (R2)
- S3 (경계): A 1개·B 1개 → B 1개 취소 → 줄은 A 하나 (R3)
- S4 (경계): A 2개 → A 1개씩 두 번 취소 → 상태 cancelled, 이벤트 order.cancelled 한 번 (R3)
- S5 (오류): A 2개 → A 3개 / 0개 / -1개 / C 1개 취소 → ValueError, 주문·재고 그대로 (R4)
- S6 (오류): 결제된 주문 → 취소 → OrderError (R4)

## 제약
- 기존 함수(create_order, pay, cancel, get_order, list_orders)의 인자와 반환은 바꾸지 않는다.
- 프로젝트 규칙: 주문 상태가 바뀌면 `events.publish("order.<새 상태>", {"order_id": id})` 를 한 번 부른다.
- 프로젝트 규칙: 금액은 원 단위 정수. 할인은 내림.

## 범위 밖
- 결제된 주문의 부분 환불
- 같은 상품 줄 합치기

## 바꿀 곳
- orders.py — cancel_items 추가
- test_orders.py — 시험 추가 (시험)
- 합계: 소스 파일 1개, 모듈 1개 (inventory.py 는 기존 release 호출만)

## 완료 기준
- [ ] C1 S1–S3 시험 통과 — `<시험 명령> <부분 취소 시험>` (R1, R2, R3, R5)
- [ ] C2 S4: 이벤트 order.cancelled 가 정확히 한 번 (R3, 제약)
- [ ] C3 S5–S6: 오류와 함께 주문·재고 그대로 (R4)
- [ ] C4 기존 검사 — `<시험 명령>` 모두 통과

## 결정과 이유
- D1: 같은 상품 줄이 둘이면 첫 줄부터 줄인다. 지금 주문 만들기가 같은 상품을 합치지 않아(orders.py:28) 드문 경우이고, 사용자가 이 방식을 골랐다.
- D2: 마지막 줄을 빼면 별도 오류 대신 주문을 취소한다. 「빈 열린 주문」이 생기지 않게 하기 위해서다.
```
