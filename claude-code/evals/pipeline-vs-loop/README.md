# 파이프라인 대 단일 루프 비교 평가

omni-pipeline의 「팀장 + 구현·리뷰어 서브에이전트」 구조가 같은 작업에서 단일 에이전트 루프보다 나은지, 그 대가(비용·시간)는 얼마인지 잽니다. 근거가 된 글: Anthropic, [Building agents: When to fold subagents into your main agent loop](https://claude.com/blog/building-agents-when-to-fold-subagents-into-your-main-agent-loop).

## 비교하는 구성

같은 모델, 같은 플러그인(`plugins/omni-pipeline`), 같은 작업 지시로 돌립니다.

| 구성 | 실행 | 의미 |
| --- | --- | --- |
| A | `--agent omni-pipeline:lead` | 지금 구조: 팀장이 SPEC을 쓰고 구현·리뷰어 서브에이전트에 맡김 |
| B | Agent 도구 금지 | 단일 루프: 한 세션이 SPEC·구현·검토를 모두 함 |
| C | 지시로 리뷰어만 사용 | 단일 루프 + 마지막 검증만 리뷰어 서브에이전트 |

- 사람 없이 돌도록, 세 구성 모두 「질문하지 말고 가정은 SPEC에 적고 진행, 끝나면 main에 커밋」을 덧붙입니다(`run.py`의 `COMMON`).
- 채점은 main의 결과로 합니다. main이 그대로면 바뀐 worktree 중 가장 최근 것을 채점하고, 표의 「채점한 곳」에 그렇게 적습니다.

## 폴더

- `fixture/`: 작업을 시작하는 예시 저장소. 메모리에 사용자·재고·가격·주문·이벤트를 두는 작은 쇼핑 앱입니다(표준 라이브러리만). `AGENTS.md`의 프로젝트 규칙(감사 기록, 상태 변경 이벤트, 정수 금액, 공개 함수 호환)은 작업 지시에 나오지 않으며, 규칙을 지키는지도 봅니다.
- `tasks/<작업>/prompt.md`: Claude에게 주는 지시
- `tasks/<작업>/hidden_test.py`: Claude에게 보여 주지 않는 합격 시험
- `tasks/<작업>/reference/`: 시험이 공정한지 확인하는 정답 구현(바뀐 파일만). Claude에게는 주지 않습니다.
- `check_tasks.py`: 작업마다 숨긴 시험이 시작 상태에서는 실패하고 정답 구현에서는 모두 통과하는지 확인합니다(토큰을 쓰지 않음). 작업을 더하거나 고친 뒤 돌립니다.
- `run.py`: 실행과 채점

## 실행

필요한 것: `claude`(로그인된 상태), `git`, Python 3. 실행할 때마다 API 토큰을 씁니다. `--budget`이 한 번 실행의 비용 상한입니다(`claude --max-budget-usd`).

```bash
python3 check_tasks.py
python3 run.py --tasks soft-delete --arms A,B,C --repeat 1 --out ~/eval-runs/pilot-1
python3 run.py --tasks all --arms A,B,C --repeat 3 --out ~/eval-runs/full-1
```

- 실행마다 `--out` 아래에 새 git 저장소를 만들고, 그 안에서 `claude -p`를 돌립니다(편집 자동 허용, 그 폴더 밖은 건드리지 않음).
- 결과: 실행별 `stream.jsonl`(Claude의 전체 기록), `row.json`, 그리고 `summary.json`과 표(표준 출력)
- 표의 열: 숨긴 시험 통과 수, 기존 시험 실패 수, 비용, 시간, 턴 수, 부른 서브에이전트, 채점한 곳

## 작업

`soft-delete`는 파일럿용 쉬운 작업이고, 나머지 10개는 여러 모듈이 얽히거나 빠뜨리기 쉬운 조건이 있는 작업입니다.

| 작업 | 내용 | 빠뜨리기 쉬운 것 |
| --- | --- | --- |
| `soft-delete` | 소프트 삭제 `delete_user`: 목록에서 빼기, 조회 시 `Gone`, 두 번 삭제해도 첫 시각 유지 | 규칙: 삭제도 감사 기록 |
| `partial-cancel` | 주문 일부 수량 취소: 재고 해제, 합계 재계산 | 쿠폰 최소 금액 아래로 내려가면 할인 0, 마지막 줄을 빼면 주문 취소 + 규칙: 상태 이벤트 한 번 |
| `expire-orders` | 오래된 미결제 주문 만료 | 정확히 경계 시각, 다시 불러도 한 번만, 규칙: 상태 이벤트 |
| `user-email` | 사용자 이메일: 정규화, 대소문자 무시 중복 금지, 변경, 찾기 | 기존 `create_user(name)` 호환, 자기 이메일 대소문자만 바꾸기 허용, 규칙: 변경도 감사 기록 |
| `save-load` | 상태를 JSON으로 저장·불러오기 | 다음 id 이어 붙이기, 예약 재고, 저장 실패 시 원래 파일 보존 |
| `page-orders` | 커서로 주문 페이지 나누기 | 중간에 새 주문이 생겨도 밀리지 않기, 잘못된 커서, 규칙: 기존 `list_orders` 그대로 |
| `refund-split` | 할인을 줄별로 나눠 환불액 계산 | 합계가 정확히 맞기(최대 나머지 방식), 같은 나머지면 앞 줄, 규칙: 정수 금액 |
| `event-retry` | 구독자 실패에도 다른 구독자에게 전달, 3번 재시도, 실패 기록 | 주문 생성이 망가진 구독자 때문에 깨지지 않기 |
| `csv-import` | CSV로 사용자 한꺼번에 들이기 | BOM, 따옴표 안 쉼표, 빈 줄 포함 줄 번호, 전부 아니면 아무것도, 규칙: 생성마다 감사 기록 |
| `price-history` | 적용 시작 시각이 있는 가격 | 같은 시각 덮어쓰기, 주문은 만든 시각의 가격 |
| `stock-alert` | 재고 부족 알림 | 경계(같으면 알림 없음), 내려가는 순간 한 번, 회복 뒤 다시 |

## 파일럿 결과

`soft-delete` 한 작업, 구성마다 1번. Claude Code 2.1.332, 모델 sonnet(서브에이전트도 sonnet), 2026-11-26.

| 구성 | 숨긴 시험 | 기존 시험 실패 | 비용($) | 기다린 시간(s) | 턴 | 부른 서브에이전트 |
| --- | --- | --- | --- | --- | --- | --- |
| A | 6/6 | 0 | 0.27 | 61 | 20 | implementer 1, reviewer 1 |
| B | 6/6 | 0 | 0.09 | 25 | 5 | — |
| C | 6/6 | 0 | 0.16 | 36 | 8 | reviewer 1 |

- 세 구성 모두 지시에 없던 프로젝트 규칙(삭제 감사 기록)까지 지켰습니다. 이 작업은 품질 차이를 가르기에 너무 쉽습니다.
- 비용과 시간은 A가 B의 약 2.9배·2.4배, C가 약 1.7배·1.4배입니다. 첫 번째 파일럿(부모 세션 변수가 새던 실행)도 비슷한 비율이었습니다(A 0.34, B 0.15, C 0.17달러).
- 이 버전의 `claude -p`는 서브에이전트를 백그라운드로 돌리고(모델이 요청하지 않아도), 끝나면 이어서 진행합니다. 그래서 A·C는 결과 이벤트가 여러 번 나옵니다.
- 한 번씩만 돌린 결과라 우연의 차이를 가를 수 없습니다.

## 어려운 작업 실측

`partial-cancel`, `refund-split`, 구성마다 1번. 조건은 파일럿과 같음(2026-11-26).

| 작업 | 구성 | 숨긴 시험 | 비용($) | 기다린 시간(s) | 턴 | 부른 서브에이전트 |
| --- | --- | --- | --- | --- | --- | --- |
| partial-cancel | A | 7/7 | 0.20 | 42 | 10 | implementer 1 |
| partial-cancel | B | 7/7 | 0.12 | 30 | 5 | — |
| partial-cancel | C | 7/7 | 0.22 | 50 | 9 | reviewer 1 |
| refund-split | A | 5/5 | 0.23 | 64 | 11 | implementer 1 |
| refund-split | B | 5/5 | 0.14 | 38 | 7 | — |
| refund-split | C | 5/5 | 0.22 | 55 | 9 | reviewer 1 |

- 세 구성 모두 모든 숨긴 시험과 지시에 없던 규칙(상태 이벤트, 정수 금액)을 통과했습니다. 이 모델에는 이 작업들도 품질 차이를 가를 만큼 어렵지 않았습니다.
- A의 팀장은 두 작업 모두 리뷰어를 부르지 않았습니다(한 번은 "별도 리뷰어 단계는 돌리지 않고 diff를 직접 읽어 확인"). 지금 구조에서 리뷰는 팀장의 판단에 따라 빠질 수 있습니다.
- 비용은 B가 A보다 약 40%, 시간은 약 30% 적었습니다. 이 수준이면 전체 평가(90번)는 약 17달러로 추정됩니다(추정치).

전체 평가는 어려운 작업 10개 × 구성 3개 × 3번(90번 실행)입니다. `--tasks all`은 `soft-delete`까지 11개(99번)를 돌리니, 어려운 작업만 돌리려면 이름을 쉼표로 나열합니다. 판단 기준은 미리 정해 둡니다:

- B가 A와 완료 수가 같거나 1개 이내로 뒤지고 더 싸고 빠르면, 작은·중간 변경은 단일 루프를 기본으로 한다.
- 함정 작업에서 C(또는 A)가 B보다 확실히 나으면, 리뷰어 서브에이전트는 남긴다.
- 총점만 보지 말고, 구성에 따라 통과·실패가 갈린 작업을 본다.
